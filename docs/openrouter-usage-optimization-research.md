# OpenRouter usage optimizations: latency, caching, reasoning

Actionable notes from OpenRouter's current first-party guidance. Provider behavior and cache support vary by model and endpoint; check current model/provider details before depending on a setting.

## Latency and routing

- **Choose the routing objective explicitly.** The default provider strategy prioritizes price while accounting for recent outages, and load-balances among stable low-cost providers. `provider.sort` can instead prioritize `price`, `throughput`, or `latency`, but explicit sorting disables that default load balancing. Use it when that objective matters more than default balancing. [Provider routing](https://openrouter.ai/docs/guides/routing/provider-selection#provider-sorting)
- **Set soft performance preferences to avoid bad tails.** `preferred_max_latency` and `preferred_min_throughput` promote endpoints meeting the specified threshold/percentile, based on a rolling five-minute window in the latency guide. These are preferences, not hard limits: the router can still use the best available option if none qualify. For example, `preferred_max_latency: {"p90": 2.5}` or combine `sort: {"by":"price"}` with `preferred_min_throughput: {"p90":40}`. [Latency cookbook](https://openrouter.ai/docs/guides/best-practices/latency-and-performance#the-latency--dx-optimization-cookbook) · [Provider threshold semantics](https://openrouter.ai/docs/guides/routing/provider-selection#performance-thresholds)
- **For acceptable fallback models, remove model grouping when speed wins.** `provider.sort: {"by":"throughput","partition":"none"}` sorts endpoints across all listed models together rather than trying every endpoint of the first model before the next. This can choose a different model from the preferred order; use only when those candidates are interchangeable for the task. [Provider routing: partition](https://openrouter.ai/docs/guides/routing/provider-selection#advanced-sorting-with-partition)
- **Keep large agent prompts cache-friendly.** Send a consistent `session_id` across turns (up to 256 characters), keep reusable system/context/tool-definition prefixes byte-identical and put changing content later. OpenRouter's best-practice guide describes a 10-minute best-effort provider pin for warm KV caches. Avoid `provider.order` when relying on that stickiness: manual ordering takes priority and disables sticky reordering. Sticky routing is best-effort; outages can trigger fallback, and Auto Exacto may change provider on tool requests. [Latency cookbook](https://openrouter.ai/docs/guides/best-practices/latency-and-performance#recipe-3-autonomous-agent-loops--large-contexts) · [Prompt caching: sticky routing](https://openrouter.ai/docs/guides/best-practices/prompt-caching#provider-sticky-routing)
- **Reduce oversized tool prefixes.** For tool-heavy agents, the latency guide recommends `openrouter:tool_search` with `defer_loading: true` for infrequently used tools so only loaded tools enter the prompt. This reduces the cacheable prefix and the work on cold starts; defer tools only if the agent can retrieve them when needed. [Latency cookbook](https://openrouter.ai/docs/guides/best-practices/latency-and-performance#recipe-3-autonomous-agent-loops--large-contexts)
- **Diagnose gateway-side latency before tuning blindly.** OpenRouter says a new region's edge caches can take roughly 1–2 minutes to warm. It also reports more aggressive cache expiry (and added latency) when account balance is low or a key approaches its credit limit. A failed primary/fallback attempt adds latency to that request. [Latency considerations](https://openrouter.ai/docs/guides/best-practices/latency-and-performance#performance-considerations)

## Prompt caching

- **Reuse stable prefixes and retain provider affinity.** Caching can reduce repeated prompt cost and prefill; most providers enable it automatically, but some require explicit markers. OpenRouter's cache stickiness is account/model/conversation scoped, resets after successful use, expires after 10 minutes idle, and yields to manual `provider.order`. Use `session_id` when opening messages change between turns; body field or `x-session-id` header works for chat/Responses, with a 256-character maximum. [Prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching)
- **Measure actual hits and spend.** Inspect response `usage.prompt_tokens_details.cached_tokens` and `cache_write_tokens` (Responses reports cache details under `usage.input_tokens_details`); `cached_tokens > 0` indicates reads. Check `cache_discount` or the Activity/generation detail to account for paid cache writes as well as cheaper reads. [Usage inspection](https://openrouter.ai/docs/guides/best-practices/prompt-caching#inspecting-cache-usage)
- **Anthropic: choose automatic or explicit breakpoints.** Top-level `cache_control` advances a trailing breakpoint as a multi-turn conversation grows. Per-block `cache_control` gives precise boundaries, with a limit of four explicit breakpoints; reserve those for large reusable material. Default TTL is 5 minutes; `ttl: "1h"` costs more per write (2x base input versus 1.25x for 5-minute writes) but can avoid repeat writes in longer sessions. Minimum cacheable prompt size is model-specific (documented values range from 1,024 to 4,096 tokens); shorter prompts are not cached. [Anthropic caching and minimums](https://openrouter.ai/docs/guides/best-practices/prompt-caching#anthropic-claude)
- **OpenAI: account for paid writes on newer models.** Automatic caching requires no setup and has a 1,024-token minimum. The docs state GPT-5.6 and later charge cache writes at 1.25x input price, while cache reads cost 0.25x or 0.50x depending on model. For a one-off prompt on these models, set `prompt_cache_options: {"mode":"explicit"}` and omit all `prompt_cache_breakpoint` markers to disable caching and its write charge. Explicit boundaries are supported on GPT-5.6+ and have a minimum 30-minute TTL. [OpenAI caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching#openai) · [Disabling caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching#disabling-prompt-caching)
- **Provider-specific support is not interchangeable.** For example, the docs say Alibaba Qwen requires explicit `cache_control` markers (5-minute TTL; 1.25x writes, 0.1x reads) and list supported model slugs; some snapshot endpoints are excluded. Validate the model's section before assuming automatic caching or porting TTL controls across providers. [Alibaba Qwen caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching#alibaba-qwen)

## Reasoning tokens and output budgets

- **Tune reasoning to the task, using per-model capabilities.** `reasoning.effort` supports levels such as `low`, `medium`, `high` on documented OpenAI reasoning and Grok models; the guide describes approximate allocations of 20%, 50%, and 80% of `max_tokens` respectively. `reasoning.max_tokens` is available for supported Gemini, Anthropic, and some Qwen models. These are not universal controls: inspect each model's `reasoning` metadata from [`GET /api/v1/models`](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens#discovering-per-model-reasoning-options) for supported efforts, defaults, max-token support, and whether reasoning is mandatory. Lower effort/budget is a cost/latency lever, but trades away reasoning capacity; validate quality on the target task.
- **Budget visible answer tokens as well as thinking.** On most providers, `max_tokens` (or `max_completion_tokens`) covers reasoning and visible output combined. A small cap can be consumed by reasoning, yielding `finish_reason: "length"` and empty/near-empty `content` while reasoning tokens are billed. Leave enough headroom or reduce effort / set a supported reasoning budget. Detect this using `usage.completion_tokens_details.reasoning_tokens` versus `usage.completion_tokens`; for Anthropic, `max_tokens` must be greater than the reasoning budget. [Reasoning budget caveat](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens#reasoning-tokens-and-max_tokens)
- **Exclude reasoning only to control response exposure/size.** `reasoning: {"exclude":true}` omits reasoning from the returned message, but does not stop its generation, billing, or consumption of the `max_tokens` budget. Some models (including OpenAI o-series according to the guide) do not expose reasoning text at all. [Reasoning controls](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens#excluding-reasoning-tokens)
