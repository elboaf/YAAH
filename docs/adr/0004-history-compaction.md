# History compaction: summarize the oldest turns behind a token budget

YAAH replays the full persisted history on every turn
(`load_history` -> the model call). Tool results are clipped at write
time, system rows are not replayed, images are pruned, and sub-agent
transcripts stay out of the parent context — but the *text* history
still grows without bound. A long session keeps getting more expensive
per turn and eventually hard-fails at the model's context ceiling.
ZCode-style compaction closes that gap.

## Decisions

**Trigger from measured tokens, not estimates.** The DB already stores
the last call's exact `usage.prompt_tokens` per conversation
(`conversations.context_tokens`, recorded by `set_conversation_usage`
after every model call). Compaction compares that number against the
resolved context window (`get_context_window`: Settings override ->
provider report -> built-in table). No tokenizer is involved, so the
decision is exact and provider-agnostic. When the window is unknown,
the estimate fallback is ~4 chars/token over a conservative default
budget — enough to still protect small local models.

**Budget = fraction of the window, headroom for the reply.** Compaction
fires when measured tokens exceed `context * COMPACTION_TRIGGER_FRACTION`
(default 0.70). The history is compacted down to
`context * COMPACTION_KEEP_FRACTION` (default 0.40), leaving room for
the system prompt, tool plumbing, and a long reply without re-tripping
the trigger every turn.

**Old turns become a persisted system summary; the recent tail stays
verbatim.** `compaction.py` sums chars-per-message from the *cut
point* backwards until the keep budget is met; everything older is
folded into one summary message generated by a tool-free, non-streaming
`model_client.chat` call (the same provider the session already uses;
a user-configured `compaction_model` override is respected). The tail
is never read or re-written, and messages never straddle the cut: a
truncated assistant/tool pair is API-invalid, so the boundary moves to
the last user message.

**The summary replaces those rows in the DB.** Compaction is persisted
with `compact_conversation`: the folded rows are deleted, one system
row is inserted at their position, and `context_tokens` is nulled so
the next call re-measures. Delete-not-tombstone keeps every later
replay simple (no conditional filtering anywhere else) and bounds the
DB like it bounds the context. The verbatim transcript is gone — the
summary is the only carrier of that content. This is acceptable
precisely because it happens once per boundary, at summary time, under
an exact measured trigger; the alternative (filtering "compacted"
tombstones in `load_history`) would add a permanent conditional to the
hottest read path and would keep replaying the tombstones in the UI.

**Model-call loop keeps appending to the in-memory `messages` after
compaction.** The persisted summary lives in the DB, but the turn's
subsequent calls reuse the already-assembled list; only the next turn
re-loads through `load_history`. Re-running compaction mid-turn is
guarded by a monotonic per-conversation gate (one compaction per turn,
and never twice on the same `context_tokens` value).

**The user is told.** The loop emits a `compacted` event; the UI shows
a collapsible divider ("earlier context summarized to stay within the
model's window — details above this line are condensed") at the
summary's position in the transcript, rendered from the persisted
system row.

## Consequences

- Per-call prompt size is now bounded: cost per turn plateaus instead
  of growing linearly, and the provider's context-ceiling 400s stop
  happening on long sessions.
- Verbatim detail below the cut is lost by design, the same trade
  ZCode makes. The most recent ~40% of the window — where the working
  state of a task lives — is always verbatim.
- `load_history` stays a pure replay (repair + image pruning only);
  compaction is a separate, tested pass. Nothing about short chats
  changes: compaction is unreachable until history exceeds 70% of the
  window.
- The summary call is one extra non-streaming request at the moment of
  compaction. It is deliberately excluded from usage persistence (it
  is not part of the agent's context) and from step counts.
- Scheduled agents with memory enabled get the same protection for
  free on their next fire — their pinned conversations grow the same
  way normal chats do.
