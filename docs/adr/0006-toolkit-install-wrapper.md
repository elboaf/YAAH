# ADR 0006: `toolkit install` wrapper + generated INDEX.md for the toolkit manifest

Issue: #118 ("Sandbox toolkit: make state.json a real table of contents the
model reliably uses").

## Context

The toolkit (`~/.yaah/toolkit`, mounted read/write into every sandbox) has a
machine-readable manifest, `state.json`, with a documented schema
(`{"tools": {"<name>": {version, kind, check, installed_at, note}}}`) and a
prompt contract ("read state.json first; write back what you install"). In
practice the write-back half is unreliable: the model sometimes records
installs as free-form prose, skips them under time pressure, or mangles the
JSON by hand-editing it. The human decision on the issue (2026-09-27): a
**recording wrapper** for reliable write-back, plus a **generated INDEX.md**
table of contents. No bootstrap drift verifier this round.

## Design questions and answers

### Q1 — How to make write-back reliable?

**Chosen: a recording wrapper, `toolkit install <name> ...`** (PowerShell,
because PowerShell is the only runtime guaranteed present in a fresh VM).
The wrapper owns the state.json mutation: it loads, deep-merges the entry,
writes pretty JSON atomically (unique temp file), regenerates INDEX.md in the
same step, and holds a cross-process lock on the manifest for the whole
read-modify-write so concurrent installs cannot last-write-win each other. A
prompt-only contract can be ignored; a wrapper call either succeeds or
errors visibly. A bootstrap drift verifier would only *detect* missing
records after the damage, so it is deferred.

### Q2 — JSON alone, or a derived INDEX.md?

**Chosen: generate `INDEX.md` from state.json.** state.json stays the single
source of truth; INDEX.md is a derived, human/agent-readable table (name,
version, kind, where it lives, how to invoke, gotchas). It is regenerated by
every wrapper mutation and never hand-edited. Rationale: the model reliably
reads markdown tables better than nested JSON, and a reader who mangles
INDEX.md cannot corrupt the manifest. The bundle ships an INDEX.md generated
from the bundled state.json.

### Q3 — Where does the read-first → check → install → record loop live?

**Both, with different jobs.** The prompt (and `sandbox_run` tool
description) states the *contract* — check state.json/INDEX.md first, and
install through the wrapper. The `sandbox-testing` SKILL.md encodes the
*procedure* as steps. Neither teaches JSON hand-editing anymore; the code
(the wrapper) is the enforcement point.

### Q4 — What metadata does a TOC entry need?

Name, `version`, `kind` (zip | dir | script | pip | installer), `path`
(POSIX-relative location inside the toolkit), `check` (one-line PowerShell
existence test), `invocation` (how to run it), optional `note` (gotchas —
e.g. the comtypes gen-dir and real-git.exe PATH notes), and `installed_at`.
All optional except name; the wrapper stores exactly what it is given.

## Consequences

- `toolkit\bin\toolkit.ps1` (+ `toolkit.cmd` shim, already on PATH in the
  VM) implements `install|remove|list|index`. The wrapper's `-ToolkitDir`
  parameter overrides the toolkit root (the tests pass it explicitly).
- `ensure_toolkit_seed` behavior: merge + copy-once is unchanged, so bundled
  entries and user records keep surviving app upgrades. Because INDEX.md is
  copy-once, an upgrade merge that adds bundled entries regenerates INDEX.md
  so the derived table of contents cannot go stale (revised from the original
  "never overwritten once present" rule; user-installed tools are already in
  the merged manifest, so regeneration loses nothing).
- Existing manual edits to state.json remain valid; the wrapper merely makes
  the correct path the easy path.
